# FordConnect Query Beats Smartcar and Dongles

Ford has quietly reopened official, free, owner-authorized API access for individuals, and that is the data source FordFuelAlert should adopt. Ford's own developer changelog records **"2026 - January: FordConnect Query launched for personal use in NA region"**, the public Developer Program terms license "personal, non-public development use" tested "only with Your vehicle(s)", and community integrations built on it have been pulling fuel level from US ICE Fords since March 2026 ([Ford changelog](https://developer.ford.com/developer/changelog); [Ford T&C](https://developer.ford.com/terms-and-conditions); [HA community thread](https://community.home-assistant.io/t/fordconnect-query-integration-a-read-only-alternative-to-fordpass/972684)). This is a different product from the legacy FordConnect credentials Ford stopped issuing in November 2024; it costs nothing, uses standard OAuth 2.0 authorization code against Ford's consumer identity tenant, and returns a `fuelLevel` percentage and `fuelRange` with per-metric timestamps. Its real costs are operational: a mandatory re-consent every 365 days, a client secret that expires on roughly a two-year cycle, Ford-side auth outages that last hours to days, terms that let Ford revoke access without notice, and an API reference that is only visible after sign-in. Smartcar remains technically viable (its public compatibility feed lists fuel level for both the F-250 and the Expedition) and the existing `SmartcarFuelService` needs no code changes, but the blocker is Ford's web login, the documented workaround is a throwaway iOS app using Smartcar's SDK, two vehicles push the account onto a paid plan, and Ford's security team has been suspending Ford accounts linked to Smartcar as recently as April 2026. OBD-II dongles are the fallback of last resort: Bouncie is the only consumer device with a self-serve API and a documented fuel field, but 2021 Fords very likely do not answer the standard fuel PID, so whether any dongle reads fuel on these trucks must be tested empirically. Every other aggregator either routes through a Ford Pro fleet account, wraps Smartcar, or no longer exists.

## Ranked recommendation: Ford's API first, Smartcar's SDK second, a dongle only if both fail

| Rank | Option | One-time effort | Monthly cost (2 vehicles) | Data freshness | Principal risk |
|---|---|---|---|---|---|
| 1 | **FordConnect Query** (developer.ford.com, NA portal) | Register app, wait 2+ h, one browser consent per vehicle, write `FordConnectFuelService` + factory (~1–2 days of code) | **$0** ([community guide](https://github.com/marq24/ha-fordconnect-query/blob/main/docs/REGISTER_APPLICATION.md)) | Cloud-cached last-known values with per-metric `updateTime`; no wake-up ([handler code](https://github.com/marq24/ha-fordconnect-query/blob/main/custom_components/fordconnect_query/fordpass_handler.py)) | Annual re-consent, 2-year secret expiry, Ford-side outages, revocable terms, metrics removed without notice |
| 2 | **Smartcar via iOS SDK onboarding** (existing provider) | Build a throwaway Xcode app with `SmartcarAuth`, `responseType: "none"`, capture `userId`; no backend code | ~$4 (Build plan, $1.99/vehicle); $0 for one vehicle on Free ([pricing](https://smartcar.com/pricing)) | Varies by make; Smartcar warns latency "may vary between makes and models" | Ford web-auth fragility, Ford suspending Smartcar-linked accounts, ticket support gated to paid plans |
| 3 | **Bouncie OBD-II dongle** | Buy device, register at bouncie.dev, OAuth consent, write provider with refresh-token store | $16 plus $179.98 hardware ([bouncie.com/health](https://www.bouncie.com/health)) | Last ignition-on reading; device checks in "every few hours" while parked ([Bouncie help](https://help.bouncie.com/en/articles/9797549-device-health-and-location)) | Fuel on 2021 Fords unproven; Trustpilot 1.3/5; Ford manual disclaims warranty for plug-in devices |

The ranking turns on one fact: FordConnect Query is the only path that satisfies the hard constraints (official owner-authorized OAuth, no stored Ford credentials, nothing unofficial) **and** bypasses the Ford web-login failure that has blocked Smartcar since July. Smartcar's Ford connector and FordConnect Query both end at Ford's Azure AD B2C consumer-identity tenant, but through different policies and entry points; the June 2026 Query consent outage (`AADB2C90027`) and Smartcar's July–October Ford web-auth incident appear in no shared thread and look independent ([Issue #37](https://github.com/marq24/ha-fordconnect-query/issues/37); [Smartcar incident](https://brandreliability.smartcar.com/incidents/c3n88sb87hm4)). Smartcar earns second place because the code already exists and the SDK workaround is confirmed from source, but it is a worse long-term home for an unattended alert: Ford's security tooling treats Smartcar connections with suspicion, and Smartcar itself was acquired by Everyday Electric in 2026 ([Smartcar pricing banner](https://smartcar.com/pricing)). Dongles rank last not on cost but on uncertainty: no vendor publishes a per-model fuel coverage list except Teltonika, and the technical evidence says generic devices will show nothing on these trucks.

A sensible sequence is to start the Ford developer registration today (it has a multi-hour to multi-day propagation delay) and, while waiting, decide whether the Smartcar SDK experiment is worth an evening as a hedge. Do not buy hardware unless both OAuth paths fail.

## Ford reopened personal-use API access in January 2026 under a new name

The premise that individuals cannot get Ford credentials dates from Ford support's November 5, 2024 reply that "a decision has been made to no longer provide credentials and access for FordConnect... If this changes in the future, we will update developer.ford.com" ([MachEforum](https://www.macheforum.com/site/threads/ford-developer-api.40081/)). Ford updated the site exactly as promised. The changelog now lists three entries: FordConnect Query launched September 2025, "launched for personal use in NA region" in January 2026, and vehicle images added in April 2026 ([Ford changelog](https://developer.ford.com/developer/changelog)). The API catalogue describes FordConnect Query as enabling developers "to securely request data from connected vehicles with explicit customer authorization" via "industry-standard OAuth 2.0 authorization code flow and granular scopes", and Ford's own use-case page promises to "check a vehicle's fuel level, door locks, vehicle information remotely" ([developer.ford.com/apis](https://developer.ford.com/apis); [developer.ford.com](https://developer.ford.com/)). The Terms and Conditions are written for "the individual or legal entity", grant "a personal, revocable, limited, non-exclusive, non-transferable license" for "personal, non-public development use only", and restrict vehicle testing to "Your vehicle(s)" — a description that fits a single-owner FordFuelAlert deployment precisely and would not cover sharing a client ID with other owners ([Ford T&C](https://developer.ford.com/terms-and-conditions)).

Registration is free, and the process is documented only by the community because the portal is a sign-in-gated SPA. The de-facto reference is marq24's Home Assistant integration guide: create a Ford developer account (MFA required; profile name must be plain letters, digits and spaces because accented characters break credential generation), open the North America portal at `developer.ford.com/developer-na`, tick the personal-use option, select all vehicle types and "All Available Data Categories", supply a redirect URL that is either `localhost` or publicly reachable, pass the CAPTCHA, and record the Client ID and Secret; Ford's backend then needs "at least 2 hours" and some users waited days ([REGISTER_APPLICATION.md](https://github.com/marq24/ha-fordconnect-query/blob/main/docs/REGISTER_APPLICATION.md)). Known traps: a 400 error referencing `businessName` is fixed by entering your full name in the company field, ports in the redirect URL cause "404 Error validating provided info", and multiple comma-separated redirect URLs do not work ([HA thread](https://community.home-assistant.io/t/fordconnect-query-integration-a-read-only-alternative-to-fordpass/972684); [evcc discussion](https://github.com/evcc-io/evcc/discussions/25639)). One US user saw an "At this time, we are no longer accepting sign-ups for the FordConnect API" banner on January 21, 2026 — almost certainly the legacy product page, days after the NA personal-use launch — and by July 2026 a US owner of a 2024 ICE F-150 had registered through `/developer-na` and was receiving telemetry ([Issue #17](https://github.com/marq24/ha-fordconnect-query/issues/17); [Issue #42](https://github.com/marq24/ha-fordconnect-query/issues/42)).

The data shape is right for this project. Community code reads a single `GET /fcon-query/v1/telemetry` document from `https://api.vehicle.ford.com` with per-metric values and `updateTime`s: `fuelLevel` (percent, explicitly "can exceed 100%" and "not clamped or filtered" by the integration), `fuelRange` (kilometres), `odometer`, `ignitionStatus`, `position`, 12 V `batteryStateOfCharge`, oil life and tyre pressures, plus `/garage` for the vehicle list ([const.py](https://github.com/marq24/ha-fordconnect-query/blob/main/custom_components/fordconnect_query/const.py); [fordpass_handler.py](https://github.com/marq24/ha-fordconnect-query/blob/main/custom_components/fordconnect_query/fordpass_handler.py); [README](https://github.com/marq24/ha-fordconnect-query)). A July 2026 US F-150 dump showed several metrics updated that day while engine-oil temperature was three weeks stale, which is the key freshness lesson: Query returns what Ford's cloud last heard, never triggers a vehicle wake-up, and each metric carries its own timestamp ([Issue #42](https://github.com/marq24/ha-fordconnect-query/issues/42)). No source covers a 2021 F-250 or 2021 Expedition specifically, but both carry the 2020+ embedded FordPass Connect modem the integration requires, so the ICE signal set should match.

The auth model has two clocks the owner must track. Ford's developer team wrote in October 2026 that "FordConnect requires users to perform account-linking every year": refresh tokens stop being issued 365 days after the `auth_time` claim in the `id_token`, and Ford "cannot adjust, extend, or grant exceptions" ([Release 2026.10.0](https://github.com/marq24/ha-fordconnect-query/releases/tag/2026.10.0); [Issue #52](https://github.com/marq24/ha-fordconnect-query/issues/52)). The client secret has a separate expiry shown in the portal — an app registered in January 2026 shows 2028-01-18 ([Issue #52](https://github.com/marq24/ha-fordconnect-query/issues/52)). Access-token lifetime for Query is undocumented; the legacy v3 API used 20 minutes, so a 2-hour timer must refresh on every run ([fordconnect-node-red](https://flows.nodered.org/node/@tally/fordconnect-node-red)). Rate limits are generous relative to this workload: the only hard datum is a live 429 body from `/garage` reading "Rate limit exceeded. Please wait 30 seconds before retrying", community integrations poll every 60 seconds (minimum 30) without bans, and evcc caches for 15 minutes ([ioBroker log](https://forum.iobroker.net/post/1349476); [const.py](https://github.com/marq24/ha-fordconnect-query/blob/main/custom_components/fordconnect_query/const.py); [evcc docs](https://docs.evcc.io/en/vehicles/ford-fordconnect-query.md)). A 2-hour cadence is roughly 120 times slower than what the community runs. The one vehicle-side throttle worth knowing about is that after about five days of 60-second polling, a US F-150 owner's FordPass app announced it was "disabling truck polling to conserve battery" and data stopped updating — a cloud/vehicle policy, not an API quota, and not a plausible outcome at 12 polls a day ([Issue #42](https://github.com/marq24/ha-fordconnect-query/issues/42)).

The risk profile is operational rather than policy. Ford's consent flow failed for apparently all users June 17–18, 2026 (`AADB2C90027`, fixed by Ford without comment), users were told to re-authenticate in late July with entities unavailable for about a day, intermittent 400s against the token endpoint recurred in September and October, odometer disappeared from the feed in September, and battery power/temperature became "no longer supported" in October — all consistent with the footer "APIs subject to change without notice" ([Issue #37](https://github.com/marq24/ha-fordconnect-query/issues/37); [Issue #47](https://github.com/marq24/ha-fordconnect-query/issues/47); [Issue #48](https://github.com/marq24/ha-fordconnect-query/issues/48); [developer.ford.com/apis](https://developer.ford.com/apis)). Importantly, no 2026 report of Ford rejecting a personal-use application, revoking Query access, or suspending a FordPass account because of Query usage was found; the integration author argues official OAuth "should keep the FordPass account safe from temporary suspension", in contrast to the reverse-engineered FordPass route ([FORDPASS_VS_FORDCONNECT.md](https://github.com/marq24/ha-fordpass/blob/main/doc/FORDPASS_VS_FORDCONNECT.md)). The terms do reserve Ford's right to charge fees and to terminate "with or without advance notice", so the 2024 shutdown could recur ([Ford T&C](https://developer.ford.com/terms-and-conditions)).

Ford's commercial channels are not an alternative for a private owner. Ford Pro Telematics is a dashboard product at **$20 per vehicle per month** with a complimentary Essentials tier, but enrollment is a business sign-up (company name and address, reviewed by the Ford Pro Intelligence Business Center) and neither tier is an API ([Ford Pro telematics](https://www.fordpro.com/en-us/telematics/); [dealer mirror](https://edmurdockford.worktrucksolutions.com/p/telematics); [Ford Pro job aid](https://content.fordpro.com/content/dam/fordpro/ca/en-ca/pdf/telematics/Ford-Pro-Telematics-Essentials-Training-Job-Aid.pdf)). Programmatic fuel ("remaining fuel") lives in the separate, quote-only Ford Pro Data Services, sold to 21 fleet partners such as Geotab, Samsara, Motive and Motorq ([Data Services page](https://5starford.worktrucksolutions.com/p/data-services)). Every one of those partners presumes a Ford Pro fleet account plus its own contract, typically multi-year at an industry benchmark of $20–45 per vehicle per month, and none was found selling to an individual with two personal vehicles ([Motorq](https://motorq.com/oem-connectivity/ford); [Navixy](https://navixy.com/learn-more/oem-telematics/ford-pro-integration); [GPS Insight](https://www.gpsinsight.com/blog/what-is-the-cost-of-telematics/)).

## Smartcar's API supports both trucks; Ford's login page is the only wall

Compatibility is not the problem. Smartcar's public Compatibility API, queried without credentials on 2026-10-25, lists `FORD-F-250-2019-2026-ICE-US` and `FORD-Expedition-2018-2027-ICE-US`, both with `internalcombustionengine-fuellevel`, `-range` and `-amountremaining` under the `read_fuel` permission, and the signals reference defines fuel level as "a percentage (0 - 100)" ([Compatibility API](https://compatibility.api.smartcar.com/v3/compatible-vehicles?filter[make]=FORD&filter[region]=US); [signals reference](https://smartcar.com/docs/api-reference/signals/internalcombustionengine.md)). The existing `SmartcarFuelService` already targets v3 with the client-credentials grant and `sc-user-id` header, so if a `user_id` can be obtained the function works as written.

The wall is the Connect step where the owner logs in to Ford. Smartcar's own incident page says web-based Ford authentication became unavailable on July 15, 2026 while "both Android and iOS are fully supported and working" through the mobile SDKs, that from October 15 even mobile-SDK connections failed with `error=server_error`, that a mobile fix landed October 16 while "Web-based authentication continues to be unavailable", and then a generic "Resolved" at 22:37 UTC the same day that never explicitly states web auth was restored ([Smartcar incident](https://brandreliability.smartcar.com/incidents/c3n88sb87hm4)). The owner's failure on 2026-10-25 is consistent with web auth remaining broken or re-breaking after that post.

Three unblocking routes exist, in increasing order of effort. First, escalate with the session id. Smartcar's ticket form explicitly asks for "Session IDs" as context, but ticket submission is limited to Build and Custom plans — "Free-plan users... cannot submit tickets" — so on the Free plan the only published channel is `support@smartcar.com`, which the incident's Resolved post itself names for continuing problems ([how to submit a ticket](https://smartcar.com/docs/help/how-to-submit-ticket); [incident](https://brandreliability.smartcar.com/incidents/c3n88sb87hm4)). No SLA is published and no 2026 example of a Ford session-id escalation producing a fix was found; the email should state that web auth recurred on 2026-10-25 after the October 16 Resolved post, with the session id, client id, UTC timestamp and make.

Second, and most promising, onboard once through the iOS SDK. The SDK source confirms the mechanics: `SmartcarAuth` renders Connect in a `WKWebView`, and when Connect needs an OEM login it posts a JSON-RPC `oauth` message that the SDK fulfils by opening Ford's `authorizeURL` in an `ASWebAuthenticationSession` — a system-browser context rather than Smartcar's web page — then relays the callback URL back into Connect ([OAuthCapture.swift](https://raw.githubusercontent.com/smartcar/ios-sdk/master/SmartcarAuth/OAuthCapture.swift)). The completion handler returns `userId` alongside `code`, `state`, `virtualKeyUrl` and `externalId`; the README says to "use userId with M2M access token", and `responseType: "none"` is "for flows like M2M tokens that don't need an authorization code", so no client secret is ever on the device and no code exchange is required ([ios-sdk README](https://github.com/smartcar/ios-sdk)). Smartcar's docs describe `user_id` as "a Smartcar-generated UUID that identifies this user" that becomes the `sc-user-id` header, and the M2M FAQ says credentials are "scoped to your application rather than to an individual vehicle", so a connection created through the SDK with the project's existing application id is visible to the backend exactly as a web-created one would be ([handle the response](https://smartcar.com/docs/connect/handle-the-response.md); [M2M FAQ](https://smartcar.com/docs/getting-started/how-to/m2m/faq.md)). Practically: a throwaway Xcode project with `SmartcarAuth(applicationId:redirectUri:scope:["read_fuel","read_vin","read_vehicle_info"], responseType:"none")`, run on a real iPhone (safer than the Simulator if Ford fingerprints browsers), yields the UUID that goes into `Smartcar__UserId`; `GET /v3/connections?filter[userId]=...` with a client-credentials token confirms the VINs landed ([API authentication](https://smartcar.com/docs/getting-started/how-to/api-authentication.md)). Why mobile worked while web failed is unpublished; the system-browser mechanism is a plausible explanation, not a confirmed one.

Third, rule out the Ford-account side. No public source quotes "Sorry, we experienced an error!" for a Smartcar-Ford flow, but the documented Ford-side causes of third-party login failure are account flags and lockouts. In April 2026 a Mach-E owner who enabled Smartcar for a ride-share app had their Ford account suspended "due to either suspicious activity or a violation of our Terms and Conditions", Ford had reset it three times, and another member advised making sure the car is "completely removed from the Smartcar database" ([MachEforum, Apr 2026](https://www.macheforum.com/site/threads/fordpass-3rd-part-apps-is-suspended-due-to-either-suspicious-activity.54349/)). Ordinary lockouts ("Too many login attempts", August 2026) clear with Forgot Password or Ford Account support, and Ford's official guidance for a locked account is to clear cookies, reset the password, then call 1-800-392-3673 ([Mustang6G](https://www.mustang6g.com/forums/threads/locked-out-of-fordpass-ford-com-account.232005/); [Ford support](https://www.ford.com/support/how-tos/search/I%20am%20unable%20to%20access%20Account%20Manager.%20Can%20you%20help)). The fastest discriminator is whether the owner can sign in cleanly at account.ford.com and in FordPass and whether any "suspicious activity" or reset email arrived since July; if so, the Connect page's own warning that Ford may flag the connection and reset the password is the explanation, not an outage. This history is also the strongest argument against Smartcar as the permanent home: as far back as December 2022 Smartcar said it would "switch over" to Ford's native OAuth "as soon as" it was ready, and the only Ford partnership Smartcar has announced since is a European integration in August 2025 ([MachEforum PSA thread](https://www.macheforum.com/site/threads/psa-unauthorized-api-use-can-disable-your-fordpass-account.13893/page-18); [Smartcar blog, Aug 2025](https://smartcar.com/blog/smartcar-partners-with-ford-to-expand-access-to-connected-vehicle-apis)).

Cost is modest but non-zero. The Free plan allows one connected vehicle with "limited vehicle signals" (undefined), so monitoring both trucks requires Build at "$1.99 per vehicle / application / month", about $4 a month, which also unlocks ticket support ([Smartcar pricing](https://smartcar.com/pricing)).

## Dongles pay off only if they speak Ford's non-standard fuel PID

The decisive technical fact for any OBD-II device is that modern Fords appear not to broadcast the SAE-standard fuel PID. A 2020 F-150 owner reported that PID 0x2F "wasn't returning anything", and a Ford Mondeo owner found the standard fuel PID "just isn't sent" with only the manufacturer-specific Mode 22 DID `22F42F` tracking the gauge — a reading that exceeded 100 right after refuelling ([Ford Truck Enthusiasts](https://www.ford-trucks.com/forums/1674086-fuel-level-pid.html); [RealDash forum](https://forum.realdash.net/t/obd2-ford-fuel-level-code/4568)). Torque extended-PID lists give `22F42F` scaled A×0.39216 for the 6.7L Super Duty ([torque-bhp.com](https://torque-bhp.com/community/main-forum/ford-6-7l-extended-pid-list/)). Any dongle without a Ford-specific profile will therefore show fuel level blank on these trucks, which is why every consumer vendor hedges: Bouncie says fuel is "available on most (but not all) vehicles", Zubie that "only about 80% of vehicles in the Zubie system report it" ([Bouncie help](https://help.bouncie.com/en/articles/2998579-fuel-level-notifications); [Zubie help](https://help.zubie.com/en/articles/11115674-vehicle-health-engine-battery-and-fuel-level-monitoring)). No positive or negative report of Bouncie or Zubie fuel on an F-150, F-250 or Expedition was found.

Among consumer devices, **Bouncie** is the only one with a self-serve developer portal, a documented fuel field and a living hobbyist ecosystem. Its OpenAPI spec defines `stats.fuelLevel` as "Percentage of fuel remaining in tank as reported by vehicle" on `GET /v1/vehicles`, with `stats.lastUpdated` for staleness, OAuth 2.0 authorization-code plus `refresh_token` grants at `auth.bouncie.com`, and webhooks that cover trips, MIL, battery and geozones but carry no fuel event ([Bouncie OpenAPI spec](https://raw.githubusercontent.com/jentic/jentic-public-apis/main/apis/openapi/api.bouncie.dev/main/1.0.0/openapi.json)). The device costs $89.99 with an $8 monthly plan, no activation fee ([bouncie.com/health](https://www.bouncie.com/health)). After ignition off it sleeps and "checks in with our system every few hours" to report status, signal and location — fuel refresh while parked is undocumented, so expect the last ignition-on reading, which is acceptable because fuel cannot drop while parked ([Bouncie help](https://help.bouncie.com/en/articles/9797549-device-health-and-location)). The Home Assistant integration `mandarons/ha-bouncie` maps `stats.fuelLevel` to a percent sensor and polls every 10 seconds, so a 2-hour poll is far below any undocumented limit ([ha-bouncie](https://github.com/mandarons/ha-bouncie)). Reliability sentiment is poor: Trustpilot 1.3/5 across 939 reviews, including an August 2026 complaint of webhooks "deactivated repeatedly" and a 2023 report of a unit that would not sync on a 2020 F-150 ([Trustpilot](https://www.trustpilot.com/review/www.bouncie.com)). **Zubie** is the runner-up with richer fields (`fuel_level`, `fuel_level_timestamp`, `range_remaining`) and HMAC-signed webhooks, but its portal is pitched at "developers and businesses", it was acquired by TSD Mobility in October 2025, and consumer pricing is roughly double Bouncie's ([Zubie vehicles reference](https://developer.zubie.com/reference/vehicles); [Digital Dealer](https://digitaldealer.com/news/tsd-mobility-acquires-zubie-bolsters-its-telematics-technology/167728/)).

The one device with model-specific evidence is **Teltonika**. Its official supported-vehicle list (xlsx dated 2026-09-07) marks "Ford F250 Super Duty 2008–2022" and "Ford Expedition 2018–2021" as supporting OEM fuel level in litres plus total mileage, and a newer "Expedition 2018–" row adds fuel percent and range ([Teltonika xlsx](https://wiki.teltonika-gps.com/images/7/76/OBD_supported_vehicles_2026_09_07.xlsx) via [wiki](https://wiki.teltonika-gps.com/view/OBD_supported_vehicle_list)). The catch is that this is a DIY telematics stack: the US-viable SKU is the Cat-M1 FMM003 (the FMB003 is 2G-only, the FMC003 variants lack US bands B12/B13, and the North-American FMC00A reached end of support on 2025-08-31), fed through a 1NCE SIM ("10 dollars covering 10 years", 500 MB) into self-hosted Traccar on a $5–20 VPS, with the F-250's litre value needing a tank-capacity conversion to reach a percentage ([Frequency bands](https://wiki.teltonika-gps.com/view/Frequency_Bands); [FMC00A](https://wiki.teltonika-gps.com/view/FMC00A); [1NCE](https://www.1nce.com/en-us/1nce-connect/features/500-mb-data-volume); [Traccar](https://www.traccar.org/managed-vs-self-hosted/)). Roughly $250–320 up front and about $5 a month for two trucks, but a weekend of configurator work and a server to run. **DIMO** offers a free Hobbyist developer tier "perfect for enthusiasts building for their own vehicles" at $1.25 per vehicle per month and defines a `powertrainFuelSystemRelativeLevel` signal, but its software connection for Ford is literally a Smartcar connection (so it inherits the same Ford login failure), its LTE R1 hardware route publishes no Ford-model fuel coverage, consumer data access needs a Pro subscription at $8.99 a month, and connectivity after the included two years is explicitly undecided ([DIMO pricing](https://www.dimo.org/pricing); [DIMO Smartcar connection](https://docs.dimo.org/support/software-connection/smartcar-connection); [DIMO connectivity FAQ](https://support.drivedimo.com/en-US/who-is-paying-for-the-connectivity-cost-286674)). Vyncs has no self-serve API, Carly is Bluetooth-only, Vinli stopped consumer hardware in 2018 and joined Sofico in 2026, Mojio's developer host no longer resolves, Munic sells only B2B, and Geotab, Samsara, Motive and Azuga are reseller-quoted fleet contracts ([vyncs](https://vyncs.com/product-comparison.aspx); [vin.li](https://www.vin.li/); [moj.io](https://www.moj.io/); [Munic](https://store.munic.io/documentations/get_started); [Geotab Ford features](https://support.geotab.com/oem-integration/doc/ford-features)).

Two caveats apply to any permanent dongle. Ford's owner's manual states that installing an aftermarket device that uses the DLC during normal driving "may cause interference with or even damage to vehicle systems" and that the "Warranty will not cover damage caused by an aftermarket plug-in device" ([Ford owner's manual](https://autooutlet.cz/wp-content/uploads/2023/01/19-f150-raptor-manual-en.pdf)). And a technician notes that "polling the modules via OBD will keep them awake" when the truck is off, so parasitic draw is a real concern with consumer dongles that lack proper sleep modes ([F-150 Lightning Forum](https://www.f150lightningforum.com/forum/goto/post?id=610188)).

Beyond dongles, no other legitimate aggregator supports US Ford ICE fuel for an individual. Motorq, Navixy, CerebrumX, Vinli, Car IQ and the fleet platforms all consume Ford Pro Data Services under a Ford Pro fleet identity; Wejo entered administration in July 2023; Otonomo is inside Urgent.ly after sunsetting part of its data services; Caruso is EU-only and Mobilisights is Stellantis-only; Android Auto's Car App Library exposes fuel only to an app running on a phone projected in the car; and no Ford channel exists on IFTTT, Zapier, Make or Home Assistant's official catalogue ([Motorq](https://motorq.com/oem-connectivity/ford); [Prolific North](https://prolificnorth.co.uk/?p=78907); [Urgent.ly 10-K](https://www.sec.gov/Archives/edgar/data/1603652/000095017025039411/uly-20241231.htm); [Android Car Hardware APIs](https://developer.android.com/training/cars/apps/library/car-hardware-api)).

## Integration shape: a FordConnectFuelService behind a Fuel__Provider factory

This section describes the change without code. It keeps the three existing interfaces, keeps the fake provider as the default, and copies the pattern already used by `EmailServiceFactory` and `AlertStateServiceFactory`.

### Selector and options

Replace the boolean `FuelAlert__UseFakeFuelService` with a `FuelOptions` class (`SectionName = "Fuel"`) carrying a `Provider` string and constants `FakeProvider = "fake"`, `SmartcarProvider = "smartcar"`, `FordConnectProvider = "fordconnect"`, defaulting to `"fake"`. A static `FuelServiceFactory.Create(...)` dispatches on `Provider`, throws `InvalidOperationException` with a clear message on an unknown value or missing required settings, and is registered in `Program.cs` as `services.AddSingleton<IFuelService>(provider => ...)` exactly like the email and alert-state registrations; `services.AddHttpClient()` moves out of the `else` branch and is registered unconditionally. Because the factory needs `IHttpClientFactory`, `TimeProvider` and the token store as well as `ILoggerFactory`, pass them explicitly rather than handing the factory the whole `IServiceProvider`. Removing the boolean touches `FuelAlertOptions`, `local.settings.sample.json`, the README settings table, `infra/main.bicep` and the live app settings on `func-h7733qj6ociee`; if that feels too wide for one PR, honour the legacy boolean only when `Fuel__Provider` is absent and remove it in a follow-up.

A new `FordConnectOptions` class (`SectionName = "FordConnect"`) mirrors `SmartcarOptions`:

| Setting | Purpose | Where it lives |
|---|---|---|
| `FordConnect__ClientId` | OAuth client id from the NA developer portal | App setting |
| `FordConnect__ClientSecret` | OAuth client secret; expires on the date shown in the portal (~2 years) | Key Vault `kv-h7733qj6ociee`, referenced from the app setting |
| `FordConnect__RedirectUri` | Must equal the redirect URL registered with Ford; used only in the one-time consent and the token exchange | App setting |

Logs record only whether each credential is configured, following the pattern already in `SmartcarFuelService`.

### The one-time owner authorization and its artifacts

The authorization-code flow runs once per vehicle in a browser, outside the Function. The authorize endpoint is `https://api.vehicle.ford.com/fcon-public/v1/auth/init` and a probe confirmed it validates `client_id`, `state`, `redirect_uri`, `response_type` and `scope` server-side before redirecting; the token endpoint is `.../dah2vb2cprod.onmicrosoft.com/oauth2/v2.0/token?p=B2C_1A_FCON_AUTHORIZE` on Ford's Azure AD B2C tenant with `openid offline_access` scopes ([const.py](https://github.com/marq24/ha-fordconnect-query/blob/main/custom_components/fordconnect_query/const.py); [auth/init probe](https://api.vehicle.ford.com/fcon-public/v1/auth/init)). The owner signs in with the Ford account, selects the radio button for one vehicle, scrolls and presses Consent, and is redirected with an authorization code; an error at Consent within two hours of registration means the app's global deployment is not finished ([CONFIGURE_INTEGRATION.md](https://github.com/marq24/ha-fordconnect-query/blob/main/docs/CONFIGURE_INTEGRATION.md)). The exchange yields an access token, a refresh token, and an `id_token` whose `auth_time` claim fixes the 365-day re-consent deadline. Because the consent page selects one vehicle per consent, covering both trucks means two consents and two refresh tokens; the Function today tracks a single `FuelAlert__VehicleId`, so start with one truck and treat the second as a scope extension. A small local console or script (not part of the deployed Function) is the natural home for the exchange step; its outputs are the artifacts: refresh token, `auth_time`, and the VIN from `/garage`.

### Token storage and rotation

This is the first provider that needs durable token state. `SmartcarFuelService` caches a one-hour client-credentials token in process memory and simply requests another when it expires; FordConnect's refresh token is an owner credential that must survive host restarts and may be rotated on each refresh. A provider-specific `FordConnectTokenStore` (no new shared abstraction) should read and write one row in the existing Table Storage account — the account `TableAlertStateService` already uses with the Function's managed identity and the `Azure.Data.Tables` package already referenced — holding the current refresh token, the `auth_time`, and the last successful refresh time. On first run with no row, it seeds from `FordConnect__RefreshToken`; on every run it refreshes the access token, writes back whichever refresh token the response carries, and logs a warning when `auth_time + 365 days` is within 30 days. Storing an owner bearer credential in Table Storage is a conscious trade-off: it avoids adding the `Azure.Security.KeyVault.Secrets` package and a Secrets Officer role assignment, both of which the project rules require permission for; if the owner prefers Key Vault as the writable store, that is the alternative and it needs that explicit package approval. Ford's annual re-consent and the client-secret expiry cannot be automated: both require the owner to repeat manual steps, which is why the store records the dates and the owner should calendar them.

### Mapping Ford's fields onto FuelStatus

`PercentRemaining` comes from `metrics.fuelLevel.value`, clamped to the 0–100 range because Ford reports values above 100 after a fill-up and the community integration deliberately does not clamp ([fordpass_handler.py](https://github.com/marq24/ha-fordconnect-query/blob/main/custom_components/fordconnect_query/fordpass_handler.py)). `RangeMiles` comes from `metrics.fuelRange.value`, which is in kilometres, converted with the same 0.621371 factor `SmartcarFuelService` already uses; it is optional and a missing range must not suppress the fuel reading. `RetrievedAtUtc` should be `metrics.fuelLevel.updateTime` — the per-metric timestamp — not the root `updateTime`, and not the wall clock, because Query returns cached values and the fuel reading can be older than other metrics. `VehicleId` is the VIN from `/garage` or `FordConnect__Vin`. Since the hysteresis in `FuelAlertService.EvaluateAsync` is inclusive at 25 and 40, clamping keeps a 103% post-fill reading from being treated as anything but "full and reset".

### Rate limits against a 2-hour timer

Each run makes two HTTP calls — one token refresh and one `/telemetry` read — with `/garage` called only once to discover the VIN and then cached in the singleton, mirroring `_discoveredVehicleId` in the Smartcar provider. That is 24 calls a day against an API whose only observed throttle is a 30-second wait on `/garage` and whose community clients make 1,440 telemetry calls a day without bans ([ioBroker log](https://forum.iobroker.net/post/1349476); [README](https://github.com/marq24/ha-fordconnect-query)). A 429 at this cadence signals something unusual; the provider should honour a numeric `Retry-After` once if it is under a minute and otherwise treat the run as no data.

### Failure modes: null no-op versus throwing

The null no-op path (warning logged, `LastCheckedUtc` saved, no alert decision) is right for conditions that are transient or data-shaped: `fuelLevel` absent or non-numeric in the telemetry document, HTTP 429 or 5xx from `/telemetry`, timeouts, and Ford's frequent backend blips that last hours to a day ([Issue #43](https://github.com/marq24/ha-fordconnect-query/issues/43); [Issue #47](https://github.com/marq24/ha-fordconnect-query/issues/47)). A stale reading — `fuelLevel.updateTime` older than `FordConnect__MaxDataAgeHours` — should still be returned (fuel does not fall while parked) with a staleness warning, so that a vehicle-side polling pause is visible in logs without silencing alerts. One deliberate departure from `SmartcarFuelService`, which degrades every failure to null, is warranted for authentication: when the token refresh is rejected with `invalid_grant` or an `AADB2C` error, the refresh token is dead and nothing will fix itself, so the provider should throw `InvalidOperationException` so the run fails visibly rather than returning null every two hours for the rest of the year. Missing configuration throws at factory time, as the other factories do.

## Conclusion

The research reframes the problem. For two years the assumption has been that an individual Ford owner must go through an intermediary — Smartcar, a fleet platform, or a dongle — because Ford would not deal with individuals. Ford's January 2026 personal-use launch quietly removed that assumption, and the intermediaries now look worse by comparison: Smartcar's Ford connector still provokes Ford's security tooling, fleet platforms are structurally closed to a private owner, and the dongle market has consolidated into either enterprise telematics or consumer products whose Ford fuel support nobody will vouch for. The most durable design for a hobby alert is the one with the fewest parties between the truck and the Function, and that is now Ford itself.

What the owner trades for that directness is a maintenance calendar rather than a subscription: an annual consent, a biennial secret rotation, and tolerance for Ford-side outages that no one at Ford announces. The integration should be built to make those events loud — a thrown exception on a dead refresh token, a logged countdown to re-consent — because the failure mode of a fuel alert is silence, and a provider that returns null politely for a year is worse than one that breaks on the day it needs attention. Keep `SmartcarFuelService` in the tree as the second provider behind the new factory; if Ford's terms change again, the swap is one app setting.
